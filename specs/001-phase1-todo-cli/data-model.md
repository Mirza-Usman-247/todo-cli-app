# Data Model: Phase I CLI Todo Application

**Feature**: 001-phase1-todo-cli
**Date**: 2026-01-01
**Status**: Complete

## Overview

This document defines the data entities, their attributes, relationships, and validation rules for the Phase I CLI Todo application.

## Entities

### Todo

Represents a single task item in the todo list.

**Attributes**:

| Field | Type | Required | Constraints | Default | Description |
|-------|------|----------|-------------|---------|-------------|
| `id` | `int` | Yes | Positive integer, unique | Auto-generated | Unique identifier, auto-incrementing starting from 1 |
| `title` | `str` | Yes | Non-empty after strip(), max 500 chars | N/A | Brief description of the task |
| `description` | `str` | No | Max 2000 chars | `""` (empty string) | Detailed information about the task |
| `completed` | `bool` | Yes | N/A | `False` | Status indicator (True if complete, False if incomplete) |
| `created_at` | `str` | Yes | ISO 8601 format | Auto-generated | Timestamp when todo was created |
| `updated_at` | `str` | Yes | ISO 8601 format | Auto-generated | Timestamp when todo was last modified |

**Python Type Definition**:
```python
from dataclasses import dataclass

@dataclass
class Todo:
    id: int
    title: str
    description: str
    completed: bool
    created_at: str
    updated_at: str
```

**Validation Rules** (enforced in service layer):

1. **Title Validation**:
   - MUST NOT be empty after stripping whitespace
   - MUST NOT exceed 500 characters
   - Whitespace-only titles are rejected

2. **Description Validation**:
   - MAY be empty (optional field)
   - MUST NOT exceed 2000 characters

3. **ID Validation**:
   - MUST be positive integer (> 0)
   - MUST be unique within the todo list
   - Auto-assigned by system, never user-provided

4. **Timestamp Validation**:
   - MUST follow ISO 8601 format (e.g., `2026-01-01T10:30:00+00:00`)
   - MUST be UTC timezone
   - Auto-generated by system, never user-provided

**Invariants**:
- `id` is immutable once assigned
- `created_at` is immutable once set
- `updated_at` changes on every modification (update title/description, toggle status)
- `completed` defaults to `False` for new todos

## State Transitions

### Create Todo
```
Initial State: N/A (todo does not exist)
Action: User provides title and optionally description
Result State:
  - id = next_id (from storage)
  - title = user input (validated)
  - description = user input or "" (validated)
  - completed = False
  - created_at = current UTC timestamp
  - updated_at = current UTC timestamp
  - next_id incremented by 1
```

### Toggle Status
```
Initial State: Todo with completed = X (True or False)
Action: User specifies todo ID
Result State:
  - completed = not X (flipped)
  - updated_at = current UTC timestamp
  - All other fields unchanged
```

### Update Content
```
Initial State: Todo with title = T, description = D
Action: User specifies todo ID and new title and/or description
Result State:
  - title = new_title (if provided) else T
  - description = new_description (if provided) else D
  - updated_at = current UTC timestamp
  - All other fields unchanged
```

### Delete Todo
```
Initial State: Todo exists in list
Action: User specifies todo ID
Result State: Todo removed from list entirely
Note: ID is NOT reused for future todos
```

## Storage Schema

### JSON File Structure

**File**: `/db/todos.json`

**Schema**:
```json
{
  "todos": [
    {
      "id": 1,
      "title": "Buy groceries",
      "description": "Milk, eggs, bread",
      "completed": false,
      "created_at": "2026-01-01T10:30:00+00:00",
      "updated_at": "2026-01-01T10:30:00+00:00"
    },
    {
      "id": 2,
      "title": "Call dentist",
      "description": "",
      "completed": true,
      "created_at": "2026-01-01T11:00:00+00:00",
      "updated_at": "2026-01-01T14:30:00+00:00"
    }
  ],
  "next_id": 3
}
```

**Top-Level Fields**:
- `todos` (array): List of todo objects
- `next_id` (integer): Next ID to assign when creating a new todo

**Empty State** (no todos):
```json
{
  "todos": [],
  "next_id": 1
}
```

## Data Flow

```
Application Startup:
  └─> Load /db/todos.json → Parse JSON → Convert to List[Todo] → Store in memory

User Operation (Create/Update/Delete/Toggle):
  └─> Modify in-memory List[Todo] → Convert to JSON → Write to /db/todos.json

Application Exit:
  └─> In-memory data already persisted after each operation
```

## Validation Error Messages

| Validation Failure | Error Message |
|-------------------|---------------|
| Empty title | "Error: Title cannot be empty" |
| Title too long | "Error: Title exceeds 500 character limit (got {length})" |
| Description too long | "Error: Description exceeds 2000 character limit (got {length})" |
| Invalid todo ID | "Error: Todo with ID {id} not found" |
| File corruption | "Warning: Data file corrupted. Created backup at {backup_path}. Starting with empty todo list." |

## Relationships

- **No relationships** in Phase I (single entity system)
- Each todo is independent
- No categorization, tagging, or grouping

## Indexes

**Primary Key**: `id` (unique, auto-increment)
**No Secondary Indexes**: Linear search acceptable for Phase I scale (<1000 todos)

## Constraints

1. **Uniqueness**: Todo IDs must be unique
2. **Immutability**: `id` and `created_at` never change after creation
3. **ID Sequence**: IDs strictly increasing; gaps allowed after deletion
4. **File Format**: All data must serialize to valid JSON
5. **Timestamp Format**: All timestamps must be ISO 8601 UTC strings

## Migration Strategy

**Phase I**: No migrations needed (initial implementation)

**Future Phases**: If data model changes:
1. Create backup of existing `/db/todos.json`
2. Write migration script to transform old format → new format
3. Validate migrated data
4. Update schema version in JSON file

## Performance Considerations

- **In-Memory Storage**: All todos loaded on startup (<1000 todos = ~1MB max)
- **Linear Search**: O(n) lookup by ID acceptable for Phase I scale
- **File I/O**: Persist on every change (small file, atomic write = <100ms)
- **Scalability**: Current design suitable for 1000-10000 todos; beyond that requires indexing
