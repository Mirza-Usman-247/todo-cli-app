# Clarifications Needed: AI-Powered Todo Chatbot

**Feature**: 003-ai-chatbot
**Date**: 2026-01-15
**Status**: Open Questions

## Purpose

This document identifies ambiguous behaviors, missing edge cases, and unresolved decisions in the AI-Powered Todo Chatbot specification that require clarification before implementation planning.

---

## Category 1: Ambiguous Chatbot Behaviors

### Q1: Vague Task References - "that task", "the task", "it"

**Current Spec State**: Unclear how chatbot should handle pronoun/demonstrative references

**Scenarios requiring clarification**:
1. User says "add a task to buy milk" then immediately says "mark it as complete" - should chatbot remember "it" refers to the just-created task?
2. User says "show my tasks" (chatbot lists 5 tasks) then user says "delete the first one" - should chatbot track list position context?
3. User says "complete that task" without prior context - is this always ambiguous or does chatbot attempt resolution?

**Questions**:
- Should the chatbot maintain **conversation context** to resolve pronouns like "it", "that task", "the last one"?
- If yes, how many messages back should context be checked (e.g., only the immediate previous exchange, or the entire conversation)?
- If a user refers to "the task I just created" 5 messages later, should chatbot still resolve it?
- When context-based resolution fails, should chatbot ask for clarification or fail with "I couldn't find that task"?

**Impact**: Affects agent prompt design and conversation history processing logic

---

### Q2: Partial Task Matching - Fuzzy vs Exact

**Current Spec State**: Examples show exact title matching ("mark buy groceries as complete")

**Scenarios requiring clarification**:
1. User has task "Buy groceries for dinner party" and says "complete buy groceries" - exact substring or fuzzy match?
2. User has tasks "Buy milk" and "Buy groceries" and says "complete buy" - ambiguous, but how to handle?
3. User types "complete groceries" but task title is "Buy groceries" - should "groceries" alone match?

**Questions**:
- Should task matching be **exact substring**, **case-insensitive substring**, or **fuzzy/semantic similarity**?
- If multiple tasks match partially (e.g., "buy" matches both "Buy milk" and "Buy bread"), should chatbot list all matches and ask for clarification?
- Should chatbot learn from user's past clarifications (e.g., user always means "Buy milk" when saying "milk")?
- What's the minimum match confidence threshold before asking for clarification?

**Impact**: Affects MCP tool design (list_tasks with filtering) and agent intent processing

---

### Q3: Conversational Confirmation Flow

**Current Spec State**: FR-038 to FR-042 require confirmations, but interaction flow unclear

**Scenarios requiring clarification**:
1. After chatbot asks "Which task do you want to complete?" with 3 options, how does user respond?
   - By typing the full task name again?
   - By typing a number (1, 2, 3)?
   - By typing "the first one" or "option 2"?
2. If user types "complete task" (ambiguous), chatbot asks clarification, then user says "never mind" - what should happen?
3. After listing tasks, user says "complete the second one" - should chatbot track the list order from the previous message?

**Questions**:
- When chatbot presents multiple-choice clarifications, what **response formats** are accepted (task name, number, position)?
- Should chatbot support **cancellation** of pending actions (e.g., "never mind", "cancel", "forget it")?
- Should chatbot maintain **ephemeral state** for the current clarification flow, or re-fetch on every response?
- How long is a clarification "active" - only for the immediate next message, or until resolved?

**Impact**: Affects conversation state management and agent multi-turn conversation handling

## Category 2: Task Explanation Edge Cases

### Q4: Task Explanation with Minimal Data

**Current Spec State**: FR-029 says "MUST NOT make assumptions beyond data stored"

**Scenarios requiring clarification**:
1. Task title: "Call" (no description) - chatbot should say "This task is to call someone" or "This task is titled 'Call'"?
2. Task title: "X" with description: "Y" (cryptic) - should chatbot attempt interpretation or just repeat the data?
3. Task created via web UI (not chatbot) with autogenerated title - chatbot has no context about intent

**Questions**:
- When task data is **minimal or cryptic**, should chatbot:
  - Simply restate the data ("Your task is titled 'Call'")?
  - Admit it can't explain ("I don't have enough information to explain this task")?
  - Suggest user add more details ("Would you like to add a description to this task")?
- Should chatbot distinguish between tasks created via chatbot vs web UI?
- If user asks "why did I create this?" and the task has no description, is the answer always "I don't have enough information"?

**Impact**: Affects agent explanation generation logic and user experience for legacy tasks

---

### Q5: Explanation Language and Tone

**Current Spec State**: FR-028 says "natural, human-friendly language" but tone undefined

**Scenarios requiring clarification**:
1. Task: "Buy groceries" with description "Urgent! Need food for tonight!" - should explanation preserve urgency tone?
2. Multiple tasks with similar titles - should chatbot compare/contrast when explaining?
3. Task with very long description (500 words) - should chatbot summarize or read verbatim?

**Questions**:
- Should explanation tone be:
  - **Neutral/informative** ("This task is for...")?
  - **Empathetic/conversational** ("You created this task because you need...")?
  - **Mirrored** from task description tone (urgent → urgent, casual → casual)?
- Should chatbot **summarize long descriptions** or always read in full?
- When task description contains multiple sentences, should chatbot extract key points or present all details?
- Should chatbot format explanations differently for completed vs pending tasks?

**Impact**: Affects agent response template design and NLG (natural language generation) strategy

## Category 3: Conversation Lifecycle Rules

### Q6: Conversation Initialization and Continuity

**Current Spec State**: FR-022 says "load conversation history" but initialization unclear

**Scenarios requiring clarification**:
1. User's first message ever - does system create a new conversation or expect frontend to create it?
2. User opens chat interface - should chatbot send a greeting first ("Hi! I can help you manage tasks") or wait for user?
3. User closes browser and returns - does conversation continue or start fresh?
4. User has 10 past conversations - which one loads? Most recent? Or always create new?

**Questions**:
- How is a **new conversation created**:
  - Frontend creates conversation_id and passes it in first request?
  - Backend auto-creates on first message from user?
  - Separate API endpoint to initialize conversation?
- Should chatbot **greet users** on conversation start or only respond to user messages?
- Should there be **one persistent conversation per user**, or multiple conversations?
- If multiple conversations allowed, how does user switch between them (conversation selector UI)?
- Should old conversations be **archived** or **deleted** after some time?

**Impact**: Affects API design, database schema (conversations table), and frontend UX

---

### Q7: Conversation History Limits

**Current Spec State**: Edge case mentions "very large conversation history" but no limits defined

**Scenarios requiring clarification**:
1. User has 1000 messages in conversation history - does system load all 1000 on every request?
2. OpenAI Agents SDK has context window limits - what happens when conversation exceeds limit?
3. User sends 50 messages in a row - does performance degrade?

**Questions**:
- Should conversation history have a **maximum message count** loaded per request (e.g., last 50 messages)?
- When conversation exceeds context window limit, should system:
  - Truncate oldest messages?
  - Summarize old messages into a context summary?
  - Archive old conversation and start fresh?
  - Fail with error message?
- Should system **paginate** conversation history on frontend (load on scroll)?
- Are there **rate limits** on messages per user per time period (to prevent abuse)?

**Impact**: Affects performance, cost (agent API usage), and database query optimization

---

### Q8: Multi-Device and Concurrent Access

**Current Spec State**: FR-021 says "stateless server" but concurrent access behavior unclear

**Scenarios requiring clarification**:
1. User opens chat on desktop and mobile simultaneously - should both see the same conversation?
2. User sends message on mobile, then immediately sends another on desktop - race condition?
3. User has chat open on two tabs - does each tab get real-time updates from the other?

**Questions**:
- Should conversation state be **synchronized across devices/tabs**?
- If yes, is this via **polling** (frontend re-fetches periodically) or **real-time** (WebSocket/SSE)?
- When concurrent requests arrive, should system:
  - Process sequentially (queue)?
  - Process in parallel with optimistic locking?
  - Allow race conditions (last-write-wins)?
- Does spec requirement for stateless server **prohibit** real-time sync features in Phase III?

**Impact**: Affects frontend architecture, API design, and potential scope expansion beyond Phase III

## Category 4: Error Scenarios and Fallback Behavior

### Q9: MCP Tool Failure Recovery

**Current Spec State**: FR-035 says "explain error without technical jargon" but recovery unclear

**Scenarios requiring clarification**:
1. User says "add task X", MCP tool fails (database timeout), chatbot explains error - should user retry manually or auto-retry?
2. MCP tool partially fails (task added to DB but response lost) - how to detect and recover?
3. User says "complete task X", tool fails, user retries - should chatbot deduplicate or execute again?

**Questions**:
- When MCP tool fails, should chatbot:
  - **Explain and stop** ("There was an error, please try again")?
  - **Auto-retry** with backoff (1-3 attempts)?
  - **Queue for later** ("I'll try again when the connection is restored")?
- Should system track **pending/failed operations** in database to prevent data loss?
- When user retries after failure, should chatbot:
  - Check if operation already succeeded?
  - Warn user about potential duplication?
  - Ensure idempotency at MCP tool level?

**Impact**: Affects error handling strategy, MCP tool idempotency design, and reliability

---

### Q10: Partial Success Handling

**Current Spec State**: Not addressed - what if operation partially succeeds?

**Scenarios requiring clarification**:
1. User says "complete all my tasks", 10 tasks exist, 7 succeed, 3 fail - what should chatbot report?
2. User says "delete old tasks", chatbot interprets as "delete completed tasks", some deletions fail - continue or rollback?
3. Bulk operation in progress when user sends another message - cancel first operation or queue second?

**Questions**:
- Should chatbot support **bulk operations** (complete all, delete all completed)?
- If yes, and partial failure occurs, should chatbot:
  - **Report partial success** ("I completed 7 out of 10 tasks. 3 failed because...")?
  - **Rollback all** (transactional)?
  - **Continue on errors** and report details?
- Should bulk operations be **atomic** (all-or-nothing) or **best-effort**?
- When bulk operation is interrupted, should it be **resumable** or **abandoned**?

**Impact**: Affects MCP tool design, transaction handling, and user experience

---

### Q11: Authentication Failure Mid-Conversation

**Current Spec State**: FR-030 requires authentication but session expiry handling unclear

**Scenarios requiring clarification**:
1. User's session expires mid-conversation - chatbot receives 401 Unauthorized - what happens?
2. User_id in request doesn't match authenticated session - security error or silent fail?
3. User logs out on another tab while chat is open - should conversation persist or clear?

**Questions**:
- When authentication fails mid-conversation, should:
  - **Frontend redirect** to login immediately?
  - **Chatbot display auth error** in-chat ("Your session has expired, please log in again")?
  - **Backend queue message** for after re-authentication?
- Should conversation history be **preserved** when user re-authenticates?
- Should system **validate auth on every message** or trust frontend session?
- What happens to **in-flight operations** when auth fails?

**Impact**: Affects auth middleware design, frontend error handling, and UX

## Category 5: Missing Acceptance Criteria

### Q12: Task Description Handling

**Current Spec State**: Acceptance scenarios only test title, not description field

**Missing scenarios**:
1. User says "add a task to buy milk for breakfast tomorrow" - should "for breakfast tomorrow" go in title or description?
2. User says "add task: call dentist, description: schedule annual checkup" - explicit delimiter?
3. User adds task via chatbot, then updates description later - how?

**Questions**:
- How does chatbot **distinguish title from description** in natural language input?
- Should chatbot:
  - Put everything in title and leave description empty?
  - Use heuristics (first sentence = title, rest = description)?
  - Always ask user to clarify ("What title and description would you like")?
- Can users **update task description separately** via chatbot ("change description of task X to Y")?
- Should chatbot show **description** when listing tasks, or only title?

**Impact**: Affects intent parsing, MCP tool parameters, and add_task/update_task design

---

### Q13: Task Priority, Due Dates, and Metadata

**Current Spec State**: Phase II likely has priority/due date fields, but chatbot interaction undefined

**Missing scenarios**:
1. User says "add high priority task" - should chatbot set priority field or ignore?
2. User says "show my tasks due today" - filtered list or unsupported?
3. Existing tasks have due dates - should chatbot mention them when listing tasks?

**Questions**:
- Should chatbot support **task metadata** (priority, due date, tags) in Phase III?
- If yes, what natural language patterns should chatbot recognize:
  - "add urgent task" → priority high?
  - "task due tomorrow" → set due_date?
  - "tag this as work" → add tag?
- If no, should chatbot:
  - Ignore metadata in user input?
  - Preserve existing metadata when updating tasks?
  - Inform user that metadata is not supported via chat?
- Should filtered listing be supported ("show incomplete tasks", "show high priority tasks")?

**Impact**: Affects scope boundary (Phase III vs Phase IV), MCP tool parameter design

---

### Q14: Multi-User Collaboration Context

**Current Spec State**: FR-033 enforces user isolation, but no collaborative scenarios

**Missing scenarios**:
1. User says "add a task for John" - should chatbot support task assignment?
2. User says "show tasks I assigned to others" - multi-user query?
3. Task was created by another user but assigned to current user - should chatbot see it?

**Questions**:
- Is task **assignment** (owner vs assignee) in scope for Phase III?
- If no, should chatbot:
  - Reject assignment requests ("I can only manage your tasks")?
  - Silently ignore assignment references?
- If yes, how does user specify assignee in natural language?
- Should chatbot distinguish between "my tasks" (owned by me) vs "assigned to me"?

**Impact**: Affects scope, database schema (assignee field), and MCP tool query logic

---

### Q15: Conversation Export and History Review

**Current Spec State**: No mention of reviewing past conversations or exporting data

**Missing scenarios**:
1. User says "what did we talk about yesterday?" - should chatbot search conversation history?
2. User wants to export conversation as text/JSON for record-keeping
3. User wants to delete conversation history for privacy

**Questions**:
- Should chatbot support **conversation search** ("what tasks did I add last week")?
- Should users be able to **export conversation history** (via UI or chatbot command)?
- Should users be able to **clear conversation history** (delete all messages)?
- If conversation is deleted, should task data remain intact (conversation ≠ tasks)?
- Should system **log conversations** for debugging or audit purposes (privacy implications)?

**Impact**: Affects scope, privacy compliance (GDPR), and data retention policies
