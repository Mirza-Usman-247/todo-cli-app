# Data Model: Phase IV Deployment Entities

**Feature**: 001-local-k8s-deploy
**Date**: 2026-01-21
**Purpose**: Define the deployment entities and their relationships for Kubernetes orchestration

---

## Overview

Phase IV deployment entities represent the infrastructure components needed to containerize and orchestrate the Todo Chatbot application. These are **deployment artifacts**, NOT application domain entities.

**Entity Categories**:
1. **Container Entities**: Docker images and build configurations
2. **Kubernetes Resource Entities**: Deployments, Services, ConfigMaps, Secrets
3. **Orchestration Entities**: Helm charts, values configurations
4. **Runtime Entities**: Pods, ReplicaSets (Kubernetes-managed)

---

## 1. Container Entities

### 1.1 DockerImage

**Purpose**: Container image containing application code and dependencies

**Attributes**:
| Attribute | Type | Description | Validation |
|-----------|------|-------------|------------|
| `repository` | string | Image repository name | `todo-chatbot-frontend` or `todo-chatbot-backend` |
| `tag` | string | Image version tag | Default: `latest`, format: `v{major}.{minor}.{patch}` |
| `imageId` | string | SHA256 image digest | Auto-generated by Docker (sha256:...) |
| `size` | integer | Image size in bytes | Frontend: < 500MB, Backend: < 800MB |
| `baseImage` | string | Parent image used | `node:20-alpine` or `python:3.13-slim` |
| `exposedPorts` | array[int] | Container ports exposed | Frontend: [3000], Backend: [8000] |
| `user` | string | Non-root user for execution | `node` (frontend), `appuser` (backend) |
| `layers` | integer | Number of image layers | Optimized via multi-stage builds |
| `created` | timestamp | Image creation timestamp | ISO 8601 format |

**Lifecycle**:
1. **Build**: `docker build` with Minikube Docker daemon (`eval $(minikube docker-env)`)
2. **Validation**: Image size check, security scan (optional)
3. **Storage**: Local Minikube registry (no push to remote registry)
4. **Usage**: Referenced by Kubernetes Deployment specs

**Relationships**:
- `DockerImage` → `KubernetesDeployment` (one-to-many: image can be used by multiple deployments/replicas)

**Validation Rules**:
```yaml
Frontend Image:
  - Base image MUST be node:20-alpine or compatible
  - Exposed port MUST include 3000
  - User MUST NOT be root
  - Size SHOULD be < 500MB
  - MUST include /health endpoint handler

Backend Image:
  - Base image MUST be python:3.13-slim or compatible
  - Exposed port MUST include 8000
  - User MUST NOT be root
  - Size SHOULD be < 800MB
  - MUST include /health endpoint handler
```

### 1.2 Dockerfile

**Purpose**: Build instructions for creating Docker images

**Attributes**:
| Attribute | Type | Description | Validation |
|-----------|------|-------------|------------|
| `path` | string | File path | `docker/frontend/Dockerfile` or `docker/backend/Dockerfile` |
| `stages` | array[string] | Multi-stage build stage names | [`builder`, `runtime`] for frontend |
| `baseImage` | string | FROM instruction image | `node:20-alpine` or `python:3.13-slim` |
| `workdir` | string | Working directory in container | `/app` (standard) |
| `copyInstructions` | array[string] | Files copied into image | `package.json`, `src/`, etc. |
| `runCommands` | array[string] | RUN instructions executed | `npm install`, `uv sync`, etc. |
| `entrypoint` | string | Container entrypoint command | `CMD ["npm", "start"]` or `CMD ["uvicorn", ...]` |
| `healthCheck` | string | Health check command (optional) | `HEALTHCHECK CMD curl -f http://localhost:3000/health` |

**Lifecycle**:
1. **Generation**: Claude Code generates Dockerfile from application analysis
2. **Validation**: `docker build` dry-run to verify syntax
3. **Optimization**: Multi-stage builds, layer caching, .dockerignore
4. **Build**: Executed to produce DockerImage

**Validation Rules**:
```yaml
All Dockerfiles:
  - MUST use multi-stage builds (if applicable)
  - MUST create non-root user
  - MUST use COPY (not ADD) for application files
  - MUST minimize layers (combine RUN commands where possible)
  - SHOULD include .dockerignore for node_modules, .git, etc.
  - SHOULD use specific version tags for base images (not :latest)
```

## 2. Kubernetes Resource Entities

### 2.1 KubernetesDeployment

**Purpose**: Declarative configuration for replica pod management

**Attributes**:
| Attribute | Type | Description | Validation |
|-----------|------|-------------|------------|
| `name` | string | Deployment resource name | `todo-chatbot-frontend` or `todo-chatbot-backend` |
| `namespace` | string | Kubernetes namespace | `todo-app` |
| `replicas` | integer | Desired pod count | Min: 1, Default: 1, Max: 10 (local constraint) |
| `image` | string | Container image reference | `todo-chatbot-frontend:latest` |
| `containerPort` | integer | Port container listens on | 3000 (frontend), 8000 (backend) |
| `resources` | object | CPU/memory requests and limits | See resource specs below |
| `livenessProbe` | object | Health check for pod restart | HTTP GET /health, 30s initial delay |
| `readinessProbe` | object | Health check for service routing | HTTP GET /health, 10s initial delay |
| `envFrom` | array[ref] | Environment variables from ConfigMap/Secret | [`configMapRef`, `secretRef`] |
| `updateStrategy` | object | Deployment update behavior | RollingUpdate (default) |
| `selector` | object | Label selector for pods | `app: todo-chatbot-{frontend|backend}` |

**Resource Specifications**:
```yaml
Frontend Resources:
  requests:
    cpu: "100m"      # 0.1 CPU core
    memory: "128Mi"   # 128 Mebibytes
  limits:
    cpu: "200m"      # 0.2 CPU core
    memory: "256Mi"   # 256 Mebibytes

Backend Resources:
  requests:
    cpu: "200m"      # 0.2 CPU core
    memory: "256Mi"   # 256 Mebibytes
  limits:
    cpu: "500m"      # 0.5 CPU core
    memory: "512Mi"   # 512 Mebibytes
```

**Lifecycle**:
1. **Creation**: `helm install` applies Deployment manifest
2. **Scaling**: `kubectl scale` or kubectl-ai changes replica count
3. **Update**: `helm upgrade` triggers RollingUpdate
4. **Deletion**: `helm uninstall` removes Deployment

**Relationships**:
- `KubernetesDeployment` → `KubernetesPod` (one-to-many: deployment manages multiple pod replicas)
- `KubernetesDeployment` → `DockerImage` (many-to-one: references container image)
- `KubernetesDeployment` → `ConfigMap` (many-to-one: sources environment variables)
- `KubernetesDeployment` → `Secret` (many-to-one: sources sensitive environment variables)

**Validation Rules**:
```yaml
Deployment Validation:
  - replicas MUST be >= 1 for high availability
  - image pull policy MUST be IfNotPresent (local images)
  - container MUST have livenessProbe defined
  - container MUST have readinessProbe defined
  - resources.requests MUST be <= resources.limits
  - selector.matchLabels MUST match pod template labels
```

### 2.2 KubernetesService

**Purpose**: Network endpoint exposing deployment pods

**Attributes**:
| Attribute | Type | Description | Validation |
|-----------|------|-------------|------------|
| `name` | string | Service resource name | `todo-chatbot-frontend` or `todo-chatbot-backend` |
| `namespace` | string | Kubernetes namespace | `todo-app` |
| `type` | string | Service type | `LoadBalancer` (required by spec) |
| `selector` | object | Pod label selector | `app: todo-chatbot-{frontend|backend}` |
| `ports` | array[object] | Port mappings | See port specs below |
| `clusterIP` | string | Internal cluster IP | Auto-assigned by Kubernetes |
| `loadBalancerIP` | string | External IP (Minikube tunnel) | `localhost` (via minikube tunnel) |

**Port Specifications**:
```yaml
Frontend Service Ports:
  - name: http
    protocol: TCP
    port: 80          # External service port
    targetPort: 3000  # Container port

Backend Service Ports:
  - name: http
    protocol: TCP
    port: 80          # External service port
    targetPort: 8000  # Container port
```

**Lifecycle**:
1. **Creation**: `helm install` applies Service manifest
2. **Access**: `minikube tunnel` exposes LoadBalancer on localhost
3. **Endpoint Updates**: Automatically updated as pods start/stop
4. **Deletion**: `helm uninstall` removes Service

**Relationships**:
- `KubernetesService` → `KubernetesPod` (one-to-many: service routes to multiple pods via selector)
- `KubernetesService` → `KubernetesDeployment` (via label selectors, not direct reference)

**Validation Rules**:
```yaml
Service Validation:
  - type MUST be LoadBalancer (per spec requirement FR-005)
  - selector MUST match deployment pod labels
  - targetPort MUST match container port in deployment
  - port 80 (external) → container port mapping required
```

### 2.3 ConfigMap

**Purpose**: Non-sensitive configuration data for applications

**Attributes**:
| Attribute | Type | Description | Example Value |
|-----------|------|-------------|---------------|
| `name` | string | ConfigMap resource name | `todo-chatbot-config` |
| `namespace` | string | Kubernetes namespace | `todo-app` |
| `data` | map[string]string | Key-value configuration pairs | See data spec below |

**Data Specifications**:
```yaml
ConfigMap Data:
  # Backend configuration
  PORT: "8000"
  NODE_ENV: "development"

  # Frontend configuration
  VITE_API_URL: "http://localhost:8000/api"

  # Common configuration
  LOG_LEVEL: "info"
  CORS_ORIGINS: "*"  # Permissive for local development
```

**Lifecycle**:
1. **Creation**: `helm install` creates ConfigMap from values.yaml
2. **Update**: `helm upgrade` can update ConfigMap data
3. **Consumption**: Pods mount ConfigMap as environment variables
4. **Deletion**: `helm uninstall` removes ConfigMap

**Relationships**:
- `ConfigMap` → `KubernetesDeployment` (one-to-many: single ConfigMap used by multiple deployments)

**Validation Rules**:
```yaml
ConfigMap Validation:
  - MUST NOT contain sensitive data (use Secret instead)
  - Keys MUST be valid environment variable names (uppercase, underscores)
  - Values MUST be strings (Kubernetes requirement)
  - PORT values MUST match container exposed ports
```

### 2.4 Secret

**Purpose**: Sensitive configuration data (credentials, tokens)

**Attributes**:
| Attribute | Type | Description | Example Value |
|-----------|------|-------------|---------------|
| `name` | string | Secret resource name | `todo-chatbot-secret` |
| `namespace` | string | Kubernetes namespace | `todo-app` |
| `type` | string | Secret type | `Opaque` (generic secret) |
| `data` | map[string]base64 | Base64-encoded sensitive values | See data spec below |

**Data Specifications** (values shown decoded; stored as base64):
```yaml
Secret Data:
  DATABASE_URL: ""  # Empty for Phase IV (no database)
  JWT_SECRET: <random-32-char-string>  # Auto-generated on helm install
  BETTER_AUTH_SECRET: <random-32-char-string>  # Auto-generated on helm install

  # Optional (if needed)
  OPENAI_API_KEY: <user-provided>  # For kubectl-ai
```

**Lifecycle**:
1. **Creation**: `helm install` generates random secrets via template functions
2. **Update**: Manual update via `kubectl edit secret` or Helm upgrade
3. **Consumption**: Pods mount Secret as environment variables
4. **Deletion**: `helm uninstall` removes Secret

**Relationships**:
- `Secret` → `KubernetesDeployment` (one-to-many: single Secret used by multiple deployments)

**Validation Rules**:
```yaml
Secret Validation:
  - MUST use base64 encoding for all values
  - MUST NOT be committed to version control with real values
  - Auto-generated secrets MUST use cryptographically secure random generation
  - JWT_SECRET MUST be >= 32 characters
  - BETTER_AUTH_SECRET MUST be >= 32 characters
```

## 3. Orchestration Entities

### 3.1 HelmChart

**Purpose**: Package containing Kubernetes manifests and configuration values

**Attributes**:
| Attribute | Type | Description | Validation |
|-----------|------|-------------|------------|
| `name` | string | Chart name | `todo-chatbot` |
| `version` | string | Chart version (semantic) | `0.1.0` (initial Phase IV release) |
| `appVersion` | string | Application version | `1.0.0` (Phase III app version) |
| `description` | string | Chart description | "Local Kubernetes deployment for Todo Chatbot" |
| `apiVersion` | string | Helm API version | `v2` (Helm 3+) |
| `type` | string | Chart type | `application` |
| `templates` | array[string] | Template file names | See template list below |
| `values` | object | Default configuration values | See values schema below |

**Template Files**:
```yaml
templates/:
  - _helpers.tpl              # Template helper functions
  - deployment-frontend.yaml  # Frontend Deployment manifest
  - deployment-backend.yaml   # Backend Deployment manifest
  - service-frontend.yaml     # Frontend Service manifest
  - service-backend.yaml      # Backend Service manifest
  - configmap.yaml            # ConfigMap manifest
  - secret.yaml               # Secret manifest (with auto-generation)
```

**Values Schema** (values.yaml):
```yaml
frontend:
  replicas: 1
  image:
    repository: todo-chatbot-frontend
    tag: latest
    pullPolicy: IfNotPresent
  resources:
    requests:
      cpu: 100m
      memory: 128Mi
    limits:
      cpu: 200m
      memory: 256Mi
  service:
    type: LoadBalancer
    port: 80
    targetPort: 3000

backend:
  replicas: 1
  image:
    repository: todo-chatbot-backend
    tag: latest
    pullPolicy: IfNotPresent
  resources:
    requests:
      cpu: 200m
      memory: 256Mi
    limits:
      cpu: 500m
      memory: 512Mi
  service:
    type: LoadBalancer
    port: 80
    targetPort: 8000

config:
  nodeEnv: development
  logLevel: info
  viteApiUrl: http://localhost:8000/api

# Secrets are auto-generated; manual override possible
secrets:
  jwtSecret: ""  # Auto-generated if empty
  betterAuthSecret: ""  # Auto-generated if empty
```

**Lifecycle**:
1. **Creation**: `helm create` scaffolding + manual template development
2. **Validation**: `helm lint` checks syntax, `helm template` renders manifests
3. **Installation**: `helm install todo-chatbot ./helm/todo-chatbot -n todo-app --create-namespace`
4. **Upgrade**: `helm upgrade todo-chatbot ./helm/todo-chatbot -n todo-app`
5. **Rollback**: `helm rollback todo-chatbot <revision>` if needed
6. **Deletion**: `helm uninstall todo-chatbot -n todo-app`

**Relationships**:
- `HelmChart` → All Kubernetes Resources (one-to-many: chart generates multiple resources)

**Validation Rules**:
```yaml
Helm Chart Validation:
  - Chart.yaml MUST be valid YAML with apiVersion: v2
  - All templates MUST pass `helm lint` with 0 errors
  - Template rendering MUST succeed: `helm template` without errors
  - Values schema MUST be documented in values.yaml comments
  - All resources MUST use template helpers for naming consistency
```

## 4. Runtime Entities (Kubernetes-Managed)

### 4.1 KubernetesPod

**Purpose**: Running container instance (managed by Deployment)

**Attributes**:
| Attribute | Type | Description | Example |
|-----------|------|-------------|---------|
| `name` | string | Pod name (auto-generated) | `todo-chatbot-frontend-5d7f8b9c4-xk2lm` |
| `namespace` | string | Kubernetes namespace | `todo-app` |
| `status` | string | Pod lifecycle phase | `Running`, `Pending`, `CrashLoopBackOff`, `Succeeded`, `Failed` |
| `containers` | array[object] | Container specifications | 1 container per pod (frontend or backend) |
| `restartCount` | integer | Number of container restarts | Target: 0 (restarts indicate issues) |
| `podIP` | string | Internal cluster IP | Auto-assigned (e.g., 172.17.0.5) |
| `nodeName` | string | Node pod is scheduled on | `minikube` (single-node cluster) |
| `createdAt` | timestamp | Pod creation time | ISO 8601 format |
| `conditions` | array[object] | Pod condition statuses | `PodScheduled`, `Initialized`, `Ready`, `ContainersReady` |

**Container Specifications** (within pod):
```yaml
Frontend Container:
  name: frontend
  image: todo-chatbot-frontend:latest
  ports:
    - containerPort: 3000
  env:  # From ConfigMap and Secret
    - PORT: "3000"
    - NODE_ENV: "development"
    - VITE_API_URL: "http://localhost:8000/api"
  resources:
    requests: {cpu: 100m, memory: 128Mi}
    limits: {cpu: 200m, memory: 256Mi}
  livenessProbe:
    httpGet: {path: /health, port: 3000}
  readinessProbe:
    httpGet: {path: /health, port: 3000}

Backend Container:
  name: backend
  image: todo-chatbot-backend:latest
  ports:
    - containerPort: 8000
  env:  # From ConfigMap and Secret
    - PORT: "8000"
    - NODE_ENV: "development"
    - JWT_SECRET: <from secret>
  resources:
    requests: {cpu: 200m, memory: 256Mi}
    limits: {cpu: 500m, memory: 512Mi}
  livenessProbe:
    httpGet: {path: /health, port: 8000}
  readinessProbe:
    httpGet: {path: /health, port: 8000}
```

**Lifecycle**:
1. **Scheduling**: Kubernetes scheduler assigns pod to node (minikube)
2. **Initialization**: Container runtime pulls image, starts container
3. **Running**: Application starts, health checks begin
4. **Ready**: Readiness probe succeeds, pod added to service endpoints
5. **Restart**: Liveness probe fails → container restarted (restartCount++)
6. **Termination**: Deployment scale-down or deletion → graceful shutdown

**Relationships**:
- `KubernetesPod` → `KubernetesDeployment` (many-to-one: pod owned by ReplicaSet owned by Deployment)
- `KubernetesPod` → `DockerImage` (many-to-one: multiple pods use same image)
- `KubernetesPod` → `KubernetesService` (many-to-many: service routes traffic to matching pods)

**Validation Rules**:
```yaml
Pod Health:
  - Status SHOULD be Running for successful deployment
  - RestartCount SHOULD be 0 (restarts indicate issues)
  - All containers MUST be Ready
  - Liveness probe MUST succeed
  - Readiness probe MUST succeed

Pod Failure Modes:
  - CrashLoopBackOff: Application startup failure (check logs)
  - ImagePullBackOff: Image not found in Minikube registry
  - OOMKilled: Memory limit exceeded (increase limits)
  - Pending: Resource constraints or scheduling issues
```

### 4.2 MinikubeCluster

**Purpose**: Local Kubernetes cluster environment

**Attributes**:
| Attribute | Type | Description | Validation |
|-----------|------|-------------|------------|
| `status` | string | Cluster state | `Running`, `Stopped`, `Paused` |
| `cpuCores` | integer | Allocated CPU cores | Min: 4, Recommended: 4-6 |
| `memory` | string | Allocated RAM | Min: 8GB, Recommended: 8-16GB |
| `diskSize` | string | Allocated disk space | Min: 30GB |
| `nodeCount` | integer | Number of nodes | 1 (single-node local cluster) |
| `kubernetesVersion` | string | Kubernetes version | 1.28+ (latest stable) |
| `enabledAddons` | array[string] | Minikube addons enabled | [`metrics-server`, `ingress-dns` (optional)] |
| `driver` | string | Virtualization driver | `docker`, `hyperkit`, `kvm2`, etc. |

**Lifecycle**:
1. **Start**: `minikube start --cpus=4 --memory=8g --disk-size=30g`
2. **Configure**: `minikube addons enable metrics-server` (optional)
3. **Tunnel**: `minikube tunnel` for LoadBalancer access
4. **Stop**: `minikube stop` (preserves cluster state)
5. **Delete**: `minikube delete` (removes cluster)

**Validation Rules**:
```yaml
Minikube Cluster:
  - CPU cores MUST be >= 4 for application deployments
  - Memory MUST be >= 8GB for Phase IV workloads
  - Disk size MUST be >= 30GB for container images
  - Status MUST be Running before deployments
  - kubectl context MUST point to minikube
```

## 6. State Transitions

### 6.1 Deployment State Transitions

```
[Initial State]
    │
    ├── helm install
    │     │
    │     v
    [Deployment Created] → ReplicaSet created → Pods scheduled
    │                                                │
    │                                                v
    │                                          [Pods Running]
    │                                                │
    │                                                ├── liveness probe fails → Container Restart
    │                                                ├── readiness probe fails → Removed from Service
    │                                                └── kubectl scale → [Scaling]
    │
    ├── helm upgrade
    │     │
    │     v
    [RollingUpdate] → New ReplicaSet → New Pods → Old Pods terminated
    │
    └── helm uninstall
          │
          v
    [Deployment Deleted] → Pods terminated → [Cleanup Complete]
```

### 6.2 Pod State Transitions

```
[Pending]  # Waiting for scheduling
    │
    v
[Scheduled]  # Node assigned
    │
    v
[ContainerCreating]  # Pulling image, starting container
    │
    ├── Success → [Running]
    │                  │
    │                  ├── livenessProbe fails → [Restarting] → [Running]
    │                  ├── Application error → [CrashLoopBackOff] → [Manual Fix Required]
    │                  ├── OOM → [OOMKilled] → [Restarting] (if retry limit not reached)
    │                  └── Graceful shutdown → [Terminating] → [Terminated]
    │
    └── Failure → [ImagePullBackOff] or [ErrImagePull] → [Manual Fix Required]
```
